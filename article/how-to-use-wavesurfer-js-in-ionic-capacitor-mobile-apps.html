How to Use Wavesurfer.js in Ionic Capacitor Mobile Apps

This article explains how Ionic and Capacitor mobile applications render local audio waveforms using the Wavesurfer.js library. Because hybrid mobile applications run inside a native WebView, accessing and decoding local device audio requires bridging native file system permissions with browser-based Web Audio APIs. Below, you will learn the mechanics of resolving local file paths, converting audio data for WebView compatibility, configuring Wavesurfer.js, and optimizing performance on mobile devices.

1. Understanding WebView File Restrictions

Capacitor apps operate inside an embedded WebView served over a local HTTP scheme (such as capacitor://localhost on iOS or http://localhost on Android). Direct access to local storage paths (e.g., file:///var/mobile/... or file:///storage/emulated/0/...) using standard fetch or HTML5 <audio> elements is blocked by native security policies and Cross-Origin Resource Sharing (CORS) rules.

To execute audio visualization locally, Wavesurfer.js requires raw audio byte streams to decode the waveform via the Web Audio API. Therefore, local files must be routed through Capacitor's native asset handler or read as binary data before being passed to Wavesurfer.js.

2. Accessing Local Audio Files

To retrieve audio stored on the device, use the @capacitor/filesystem plugin. Depending on the audio source and size, there are two primary methods to make the file accessible to the WebView:

Method A: Capacitor File URL Conversion (Recommended)

Capacitor provides a utility method, Capacitor.convertFileSrc(), which converts a device's absolute file path into a local WebView URL scheme (e.g., http://localhost/_capacitor_file_/path/to/audio.mp3).

import { Capacitor } from '@capacitor/core';

const nativeFilePath = '/path/to/local/recording.wav';
const webViewUrl = Capacitor.convertFileSrc(nativeFilePath);

Method B: Reading File as Binary/Base64

For smaller audio clips or voice recordings where streaming is not required, read the file directly into memory using the Filesystem API:

import { Filesystem, Directory } from '@capacitor/filesystem';

const fileResult = await Filesystem.readFile({
  path: 'recordings/audio.m4a',
  directory: Directory.Data,
});

// Convert Base64 string to a Blob
const byteCharacters = atob(fileResult.data as string);
const byteNumbers = new Array(byteCharacters.length);
for (let i = 0; i < byteCharacters.length; i++) {
  byteNumbers[i] = byteCharacters.charCodeAt(i);
}
const byteArray = new Uint8Array(byteNumbers);
const audioBlob = new Blob([byteArray], { type: 'audio/m4a' });
const blobUrl = URL.createObjectURL(audioBlob);

3. Initializing Wavesurfer.js

Once a valid URL or Blob is ready, Wavesurfer.js can be mounted to an HTML container element.

import WaveSurfer from 'wavesurfer.js';

// DOM container reference
const container = document.getElementById('waveform') as HTMLElement;

const wavesurfer = WaveSurfer.create({
  container: container,
  waveColor: '#4F46E5',
  progressColor: '#818CF8',
  cursorColor: '#C7D2FE',
  backend: 'WebAudio', // Required for decoding raw audio peaks in modern browsers
  height: 80,
  normalize: true,
  url: webViewUrl, // Or pass blobUrl
});

wavesurfer.on('ready', () => {
  console.log('Waveform is ready for playback and interaction');
});

4. Handling Mobile-Specific Constraints

Executing audio visualization smoothly on mobile hardware requires addressing specific resource limitations:

  • Web Audio Autoplay Policies: iOS Safari and Android Chrome engines block audio initialization without user interaction. Ensure that actions like wavesurfer.play() or initial audio decoding are tied to an explicit user touch event.
  • Pre-Computed Peaks for Long Files: Decoding large audio files (over 5–10 MB) entirely on a mobile CPU causes significant UI lag or memory crashes. For large files, extract the waveform data (peaks) beforehand or generate an array of peak numbers on the native side, passing them directly to Wavesurfer's peaks option so the client can bypass full audio decoding.
  • Component Lifecycle and Memory Cleanup: Web Audio contexts persist in memory if not explicitly closed. Always call wavesurfer.destroy() within the component teardown hook (ngOnDestroy, useEffect cleanup, or beforeUnmount) to release hardware resources.
