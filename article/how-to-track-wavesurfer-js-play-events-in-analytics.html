How to Track Wavesurfer.js Play Events in Analytics

This article provides an overview of how analytics scripts capture playback metrics from embedded third-party Wavesurfer.js audio widgets. Depending on whether the widget is directly integrated into the DOM or sandboxed within an iframe, analytics platforms capture play events through native Wavesurfer event subscriptions, underlying HTML5 media element observation, or cross-document messaging APIs.

Direct API Event Listeners

When a Wavesurfer.js player is initialized directly within the same JavaScript context as the host page, analytics scripts can hook into Wavesurfer’s built-in event bus. Wavesurfer instances expose an .on() method that emits lifecycle events:

  • wavesurfer.on('play', callback): Triggers as soon as audio playback begins.
  • wavesurfer.on('pause', callback): Emits when playback stops or finishes.
  • wavesurfer.on('timeupdate', callback): Used to track milestones (e.g., 25%, 50%, 75% completion).

Within these callback handlers, the analytics script extracts metadata such as track URL, audio duration via wavesurfer.getDuration(), and current position via wavesurfer.getCurrentTime(). The script then dispatches this payload to an analytics backend (such as Google Analytics via gtag('event', ...) or a custom telemetry endpoint).

HTML5 Audio Event Delegation

Under the hood, Wavesurfer.js frequently relies on a native HTML5 <audio> element to manage media playback. If the analytics tracker does not have direct access to the specific Wavesurfer JavaScript variable, it can observe the DOM for media events.

Standard media elements fire native play, playing, pause, and ended events. Analytics scripts can attach listeners using event capturing on the window or document object:

document.addEventListener('play', (event) => {
  if (event.target.closest('.wavesurfer-container')) {
    // Collect metrics for Wavesurfer-managed audio
  }
}, true);

Because native media events do not bubble by default, enabling the capture phase (true) allows a global analytics script to intercept play events without requiring configuration from the player itself.

Cross-Origin postMessage Communication

Third-party audio widgets are commonly embedded within an <iframe> hosted on an external domain. In this architecture, the Same-Origin Policy prevents external analytics scripts from directly reading the iframe's DOM or accessing its JavaScript objects.

To collect play events in this scenario, communication occurs across boundaries via the Window.postMessage() API:

  1. Widget Side: The Wavesurfer instance inside the iframe listens to the local play event and sends a serialized message to the parent window:

    wavesurfer.on('play', () => {
  window.parent.postMessage({
    type: 'WAVESURFER_EVENT',
    action: 'play',
    currentTime: wavesurfer.getCurrentTime(),
    duration: wavesurfer.getDuration()
  }, '*');
});

  2. Host Page Side: The host analytics script registers a global message listener to receive the data:

    window.addEventListener('message', (event) => {
  if (event.data?.type === 'WAVESURFER_EVENT' && event.data.action === 'play') {
    // Forward event data to the analytics platform
  }
});

Metrics Typically Captured

Regardless of the ingestion method, the analytics payload generated on a play event typically includes:

  • Event Action: Explicitly labeled as play or resume.
  • Track Identifier: File name, database ID, or audio source URL.
  • Playback State: Starting timestamp, total duration, and playback rate.
  • Context: Session IDs, user IDs, and container identifiers to track user engagement across multiple audio assets on a single page.
