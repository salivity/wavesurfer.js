AWS S3 CORS Configuration for Wavesurfer.js

To render audio waveforms in the browser, Wavesurfer.js uses the Web Audio API to fetch and decode raw binary audio data from remote storage. Because this process relies on asynchronous fetch or XMLHttpRequest calls across different domains, cloud storage providers like AWS S3 must explicitly serve Cross-Origin Resource Sharing (CORS) headers. Without a properly configured CORS policy on your S3 bucket, browsers will block the audio stream, preventing Wavesurfer.js from generating waveforms or playing audio.

Why Wavesurfer.js Requires CORS

Standard HTML <audio> elements can stream media across origins with minimal restrictions. However, Wavesurfer.js operates differently: it requires access to the underlying byte stream via AudioContext.decodeAudioData().

When the browser requests audio data for Web Audio API processing:

  1. It sends an Origin HTTP header identifying the domain where your web app is hosted.
  2. For certain complex requests (such as range requests), the browser may first issue an OPTIONS preflight check.
  3. The browser verifies that the storage server's response headers authorize the requesting origin to inspect the response body.

If AWS S3 does not return the proper Access-Control-Allow-Origin headers, the browser drops the response, throwing a CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource error in the developer console.

How AWS S3 Handles and Serves CORS Headers

AWS S3 evaluates incoming requests against an XML or JSON-based CORS configuration assigned to the bucket. When an incoming request includes an Origin header matching a rule in your configuration, S3 injects the corresponding access control headers into the response:

  • Access-Control-Allow-Origin: Specifies which domains are permitted to read the resource.
  • Access-Control-Allow-Methods: Specifies the HTTP methods allowed (typically GET and HEAD for audio files).
  • Access-Control-Allow-Headers: Informs the browser which HTTP request headers can be used during the actual request.
  • Access-Control-Expose-Headers: Allows the client-side JavaScript to read specific headers returned by S3, such as Content-Range or Content-Length, which are critical for seeking and streaming large audio files.
  • Access-Control-Max-Age: Tells the browser how many seconds to cache the results of a preflight OPTIONS request.

Configuring CORS in AWS S3

To enable Wavesurfer.js to access your audio files, apply the following JSON configuration in the AWS Management Console under S3 Bucket > Permissions > Cross-origin resource sharing (CORS):

[
    {
        "AllowedHeaders": [
            "*"
        ],
        "AllowedMethods": [
            "GET",
            "HEAD"
        ],
        "AllowedOrigins": [
            "https://yourdomain.com",
            "http://localhost:3000"
        ],
        "ExposeHeaders": [
            "ETag",
            "Content-Length",
            "Content-Range",
            "Accept-Ranges"
        ],
        "MaxAgeSeconds": 3600
    }
]

Key Considerations for Wavesurfer.js

  • Exposing Audio Headers: Exposing Content-Range and Accept-Ranges ensures that Wavesurfer.js and the Web Audio API can handle chunked audio and track scrubbing without decoding errors.
  • Restricting Origins: While using * in AllowedOrigins simplifies testing in development environments, production configurations should restrict origins to authorized application domains to prevent unauthorized hotlinking.
  • CloudFront and CDNs: If your AWS S3 bucket is fronted by an Amazon CloudFront distribution, CloudFront must be configured to forward the Origin, Access-Control-Request-Headers, and Access-Control-Request-Method headers to the S3 origin. Ensure your CloudFront cache policy includes these headers; otherwise, CloudFront will cache responses without CORS headers and continue serving failed requests to browsers.
