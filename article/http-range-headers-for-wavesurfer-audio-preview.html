HTTP Range Headers for Wavesurfer Audio Preview

Rendering audio preview visuals without downloading an entire media file requires HTTP byte-range requests. This article outlines the essential HTTP headers used by both the browser and the web server to enable partial content streaming for Wavesurfer.js, explains how the client and server negotiate partial data, and details the necessary Cross-Origin Resource Sharing (CORS) configurations required for successful visual rendering.

The Client Request Header: Range

To request a specific segment of an audio file rather than the entire payload, the client must include the Range request header. Wavesurfer.js typically fetches audio data via the Fetch API or an XMLHttpRequest when processing raw audio for Web Audio API decoding.

The syntax for the client header is:

Range: bytes=start-end

For example, to request the first megabyte of an audio file to parse metadata and display an initial waveform segment, the client sends:

Range: bytes=0-1048575

The Server Response Headers

For partial fetching to work, the hosting server must support byte serving and respond with the appropriate headers alongside an HTTP 206 Partial Content status code.

1. Accept-Ranges

The server advertises support for partial requests using the Accept-Ranges header in response to standard GET or HEAD requests:

Accept-Ranges: bytes

If the server sends Accept-Ranges: none, the browser knows byte-range requests are unsupported and will fall back to downloading the full file.

2. Content-Range

When responding to a valid Range request with status code 206 Partial Content, the server must indicate the byte span returned and the total file length using the Content-Range header:

Content-Range: bytes 0-1048575/15728640

This response tells Wavesurfer.js that it received bytes 0 through 1,048,575 out of a total file size of 15,728,640 bytes.

3. Content-Length

The Content-Length header in a partial response specifies the size of the returned chunk, not the entire file:

Content-Length: 1048576

CORS Headers for Range Requests

When audio files are hosted on a different domain, Content Delivery Network (CDN), or port than the web application, cross-origin resource restrictions apply. The server must provide specific CORS headers to allow JavaScript to request and read partial audio buffers:

  • Access-Control-Allow-Origin: Specifies which domains can access the resource (e.g., * or https://example.com).
  • Access-Control-Allow-Headers: Must explicitly allow the Range header (e.g., Access-Control-Allow-Headers: Range).
  • Access-Control-Expose-Headers: Must explicitly allow the frontend to read range metadata from the response (e.g., Access-Control-Expose-Headers: Content-Range, Accept-Ranges, Content-Length).

Implementation in Wavesurfer.js

To utilize partial fetching in Wavesurfer.js, configure the fetch parameters via the fetchParams option when initializing the instance:

const wavesurfer = WaveSurfer.create({
  container: '#waveform',
  waveColor: '#4F46E5',
  progressColor: '#818CF8',
  url: 'https://example.com/audio.mp3',
  fetchParams: {
    headers: {
      'Range': 'bytes=0-1048575'
    }
  }
});

Using these headers allows Wavesurfer.js to retrieve and decode only the necessary slice of audio data, significantly reducing bandwidth consumption and accelerating visual rendering times for large media files.
