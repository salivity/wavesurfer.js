Unit Testing Wavesurfer.js Components

Unit testing components that rely on Wavesurfer.js can be challenging because the library depends heavily on browser-specific environments, including the Web Audio API and the HTML5 Canvas API. This guide explains how to effectively isolate and unit test your audio player components by mocking Wavesurfer.js APIs, simulating audio events, and verifying component lifecycles in environments like Jest or Vitest with React Testing Library, Vue Test Utils, or vanilla JavaScript.

The Problem with Testing Wavesurfer.js Directly

Test runners typically execute in headless Node.js environments using JSDOM or Happy DOM. Wavesurfer.js requires native browser implementations of window.AudioContext, HTMLCanvasElement.prototype.getContext('2d'), and media element decoders. Running Wavesurfer directly in a unit test often causes crashes or silent failures because these APIs are either partially implemented or missing entirely in JSDOM.

For true unit tests, the goal is not to test Wavesurfer’s internal waveform rendering, but rather to verify that your component configures Wavesurfer correctly, responds to audio events, controls playback, and cleans up resources on unmount.

Step 1: Mocking Wavesurfer.js

The most reliable approach is to mock the wavesurfer.js package directly. This isolates your component logic and removes all dependencies on canvas and audio contexts.

Here is a standard mock setup using Jest or Vitest:

// __mocks__/wavesurfer.js (or directly in your test file)
const mockWaveSurferInstance = {
  load: jest.fn(),
  play: jest.fn(),
  pause: jest.fn(),
  playPause: jest.fn(),
  stop: jest.fn(),
  destroy: jest.fn(),
  on: jest.fn(),
  un: jest.fn(),
  once: jest.fn(),
  isPlaying: jest.fn().mockReturnValue(false),
  getCurrentTime: jest.fn().mockReturnValue(0),
  getDuration: jest.fn().mockReturnValue(100),
};

const WaveSurfer = {
  create: jest.fn(() => mockWaveSurferInstance),
};

export default WaveSurfer;
export { mockWaveSurferInstance };

Step 2: Key Behaviors to Test

Focus your test assertions on the contract between your wrapper component and the Wavesurfer instance:

1. Initialization and Options

Ensure that when your component mounts, WaveSurfer.create is invoked with the expected container element and configuration parameters (such as waveColor, progressColor, and cursorWidth).

test('initializes wavesurfer with correct options', () => {
  render(<AudioPlayer url="test.mp3" waveColor="#ff0000" />);

  expect(WaveSurfer.create).toHaveBeenCalledWith(
    expect.objectContaining({
      waveColor: '#ff0000',
      container: expect.any(HTMLElement),
    })
  );
});

2. Media Loading

Verify that the load method is called with the provided audio source URL, both during initial mount and when the source prop updates.

test('loads the provided audio URL', () => {
  render(<AudioPlayer url="sample-audio.mp3" />);

  expect(mockWaveSurferInstance.load).toHaveBeenCalledWith('sample-audio.mp3');
});

3. Playback Controls

Simulate user interactions (such as clicking play/pause buttons) and verify that the corresponding Wavesurfer methods are invoked.

test('toggles playback on button click', () => {
  render(<AudioPlayer url="sample-audio.mp3" />);

  const playButton = screen.getByRole('button', { name: /play/i });
  fireEvent.click(playButton);

  expect(mockWaveSurferInstance.playPause).toHaveBeenCalledTimes(1);
});

4. Event Subscriptions and UI Updates

Components typically register callbacks for events like ready, audioprocess, or finish. You can test these by capturing the registered callback from the on mock and invoking it manually.

test('updates UI when audio is ready', () => {
  render(<AudioPlayer url="sample-audio.mp3" />);

  // Find the callback passed to wavesurfer.on('ready', callback)
  const readyCall = mockWaveSurferInstance.on.mock.calls.find(
    (call) => call[0] === 'ready'
  );
  const onReadyCallback = readyCall[1];

  // Trigger the callback manually
  act(() => {
    onReadyCallback();
  });

  expect(screen.getByText(/ready to play/i)).toBeInTheDocument();
});

5. Teardown and Cleanup

Prevent memory leaks by confirming that destroy is called when your component unmounts.

test('destroys wavesurfer instance on unmount', () => {
  const { unmount } = render(<AudioPlayer url="sample-audio.mp3" />);
  
  unmount();

  expect(mockWaveSurferInstance.destroy).toHaveBeenCalledTimes(1);
});

Alternative: Polyfilling for Shallow Integration Tests

If you must run integration tests without mocking the entire module, provide polyfills for the missing browser APIs in your setup file:

// setupTests.js
window.AudioContext = jest.fn().mockImplementation(() => ({
  createGain: jest.fn(),
  createChannelSplitter: jest.fn(),
  close: jest.fn(),
}));

HTMLCanvasElement.prototype.getContext = jest.fn(() => ({
  fillRect: jest.fn(),
  clearRect: jest.fn(),
  getImageData: jest.fn(() => ({ data: [] })),
  putImageData: jest.fn(),
  createImageData: jest.fn(() => []),
  setTransform: jest.fn(),
  drawImage: jest.fn(),
  save: jest.fn(),
  fillText: jest.fn(),
  restore: jest.fn(),
  beginPath: jest.fn(),
  moveTo: jest.fn(),
  lineTo: jest.fn(),
  closePath: jest.fn(),
  stroke: jest.fn(),
  translate: jest.fn(),
  scale: jest.fn(),
  rotate: jest.fn(),
  arc: jest.fn(),
  fill: jest.fn(),
}));

While polyfills allow Wavesurfer to instantiate without crashing, full module mocking remains the faster, more predictable pattern for component unit tests.
