Automated Screen Reader Testing for Wavesurfer.js

This article provides a practical guide on implementing automated screen reader testing for web applications that use Wavesurfer.js. Because Wavesurfer.js relies on HTML5 <canvas> elements to render audio waveforms visually, it presents unique challenges for assistive technologies. Below, you will learn how to structure an accessible audio wrapper, validate accessibility tree states programmatically, use automation frameworks to simulate screen reader interactions, and embed these tests into your CI/CD pipeline.

The Accessibility Challenge with Wavesurfer.js

Wavesurfer.js visualizes audio using HTML5 canvas elements. Canvas elements are graphical bitmaps with no inherent semantic structure, meaning screen readers (such as NVDA, JAWS, or VoiceOver) cannot interpret the waveform, playhead position, or audio playback state directly from the rendered visuals.

To make Wavesurfer.js accessible, developers must construct a parallel semantic structure—composed of standard HTML controls, ARIA roles, and live regions—that mirrors the state of the audio player. Automated screen reader testing focuses on verifying that this semantic structure exists, updates correctly during playback, and exposes proper accessibility trees to assistive tech APIs.

Key Accessibility Requirements to Test

Before writing automated tests, ensure your Wavesurfer.js implementation provides the semantic properties screen readers require:

  1. Play/Pause Controls: Accessible buttons with dynamic labels (aria-label="Play" switching to aria-label="Pause").
  2. Current Time and Duration: Time indicators using aria-live="polite" or an accessible progress bar.
  3. Seekable Slider: A custom slider or range input representing the track position with role="slider", aria-valuemin="0", aria-valuemax="[duration]", and dynamically updating aria-valuenow.
  4. Keyboard Operability: Ability to tab to controls, space to toggle playback, and arrow keys to seek forward or backward.

Method 1: Testing the Accessibility Tree with Playwright

Modern automation frameworks like Playwright expose the browser's accessibility tree directly, allowing you to assert screen reader nodes without launching an actual screen reader.

Example: Playwright Accessibility Snapshot Test

import { test, expect } from '@playwright/test';

test.describe('Wavesurfer.js Accessibility Suite', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto('/audio-player');
    // Ensure Wavesurfer is ready
    await page.waitForSelector('[data-testid="wavesurfer-ready"]');
  });

  test('should expose correct initial screen reader tree', async ({ page }) => {
    const snapshot = await page.accessibility.snapshot();

    // Verify play button is exposed with correct role and label
    const playButton = snapshot.children.find(
      (node) => node.role === 'button' && node.name === 'Play audio'
    );
    expect(playButton).toBeDefined();

    // Verify seek slider exposes proper min, max, and current values
    const seekSlider = snapshot.children.find(
      (node) => node.role === 'slider' && node.name === 'Audio track timeline'
    );
    expect(seekSlider).toBeDefined();
    expect(seekSlider.valuemin).toBe(0);
    expect(seekSlider.valuenow).toBe(0);
  });

  test('should update ARIA states when audio plays', async ({ page }) => {
    const playButton = page.getByRole('button', { name: 'Play audio' });
    await playButton.click();

    // Verify button label changes to reflect active state
    await expect(page.getByRole('button', { name: 'Pause audio' })).toBeVisible();

    // Fast-forward playback and verify slider update
    await page.waitForTimeout(1000);
    const slider = page.getByRole('slider', { name: 'Audio track timeline' });
    const currentValue = await slider.getAttribute('aria-valuenow');
    expect(Number(currentValue)).toBeGreaterThan(0);
  });

  test('should support keyboard navigation', async ({ page }) => {
    const slider = page.getByRole('slider', { name: 'Audio track timeline' });
    await slider.focus();

    // Simulate right arrow key to seek forward
    await page.keyboard.press('ArrowRight');

    const updatedValue = await slider.getAttribute('aria-valuenow');
    expect(Number(updatedValue)).toBeGreaterThan(0);
  });
});

Method 2: End-to-End Screen Reader Automation with Guidepup

To test actual spoken output and screen reader cursoring, you can use Guidepup, an automation tool that drives real screen readers (VoiceOver on macOS, NVDA on Windows) via code.

Example: Guidepup with VoiceOver

import { voiceOver, test } from '@guidepup/playwright';
import { expect } from '@playwright/test';

test('VoiceOver reads audio player controls correctly', async ({ page }) => {
  await page.goto('/audio-player');
  await page.waitForSelector('[data-testid="wavesurfer-ready"]');

  // Start VoiceOver
  await voiceOver.start();

  // Navigate to the player controls
  await voiceOver.next();
  expect(await voiceOver.lastSpokenPhrase()).toContain('Play audio, button');

  // Activate playback using VoiceOver keyboard shortcuts
  await voiceOver.act();
  expect(await voiceOver.lastSpokenPhrase()).toContain('Pause audio');

  // Move to the timeline slider
  await voiceOver.next();
  expect(await voiceOver.lastSpokenPhrase()).toContain('Audio track timeline, slider');

  // Stop VoiceOver
  await voiceOver.stop();
});

Method 3: Static Analysis and ARIA Rule Verification with Axe-Core

Integrate @axe-core/playwright to automatically catch missing labels, invalid ARIA attributes, and keyboard trapping around the canvas container.

import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('player container should have no detectable a11y violations', async ({ page }) => {
  await page.goto('/audio-player');

  const accessibilityScanResults = await new AxeBuilder({ page })
    .include('#wavesurfer-container')
    .analyze();

  expect(accessibilityScanResults.violations).toEqual([]);
});

Integrating into CI/CD

To maintain screen reader accessibility for Wavesurfer.js:

  1. Run Axe and Accessibility Tree Tests on Pull Requests: Playwright accessibility snapshot assertions and Axe audits run headlessly on standard Linux runners in GitHub Actions or GitLab CI.
  2. Run Guidepup in OS-Specific Matrixes: When testing actual screen reader speech (e.g., VoiceOver), execute the job on a macOS runner (macos-latest).
  3. Fail Builds on Semantic Regressions: Block merges if any Wavesurfer wrapper modifications cause canvas elements to lose their associated semantic labels, timeline ARIA attributes, or keyboard focus bindings.
