Compressing Wavesurfer.js Peaks with Gzip and Brotli

Precomputing waveform peaks for Wavesurfer.js significantly speeds up client-side rendering by eliminating the need to decode entire audio files in the browser, but raw numeric peak arrays stored in JSON format can consume substantial bandwidth. By applying standard HTTP compression algorithms such as Gzip or Brotli, developers can typically achieve data size reductions between 60% and 85%. This guide breaks down expected compression ratios, the technical reasons behind these savings, and best practices for optimizing peak arrays before compression.

Understanding Wavesurfer.js Peak Data

Wavesurfer.js visualizes audio using an array of numbers representing peak amplitudes. These are typically generated on the server using tools like audiowaveform or extracted via the Web Audio API.

In standard implementations, these peaks are serialized as JSON arrays containing either floating-point numbers (ranging between -1.0 and 1.0) or integers (such as 8-bit or 16-bit values). A typical two-channel or interleaved peak dataset for a three-minute song can easily contain 1,000 to 10,000 values, creating raw JSON payloads between 50 KB and 200 KB.

Gzip Compression Savings

Gzip (using the DEFLATE algorithm) performs exceptionally well on JSON numeric data due to repeated structural characters (brackets, commas, minus signs) and recurring digit patterns:

  • Floating-Point Arrays: Standard arrays of floats with unconstrained precision (e.g., 0.12345678) typically achieve 60% to 70% reduction under Gzip level 6.
  • Quantized Floats (2–3 decimal places): Reducing float precision increases pattern repetition, lifting Gzip compression savings to 70% to 78%.
  • Integer Arrays: Arrays converted to signed or unsigned integers (e.g., -128 to 127) generally compress by 75% to 80%.

A raw 100 KB JSON peak file is routinely compressed down to approximately 20 KB to 25 KB using Gzip.

Brotli Compression Savings

Brotli outperforms Gzip when compressing numeric JSON data because of its larger sliding window (up to 16 MB versus Gzip's 32 KB) and context modeling capabilities:

  • Floating-Point Arrays: Brotli (quality level 5–11) typically yields 68% to 78% reduction on full-precision floating-point arrays.
  • Quantized Floats: Brotli achieves 75% to 83% savings when numbers are limited to two or three decimal places.
  • Integer Arrays: For quantized 8-bit integer arrays, Brotli can reach 80% to 87% reduction.

Across real-world peak files, Brotli consistently delivers payloads that are 5% to 15% smaller than Gzip, reducing a 100 KB raw file to roughly 14 KB to 18 KB.

Pre-Compression Optimization Strategies

To maximize the efficiency of either compression algorithm, apply the following optimizations to your peak data before serving:

  1. Truncate Decimal Precision: Waveform displays rarely require more than two decimal points of accuracy. Truncating values from 0.458921 to 0.46 strips unique character sequences and dramatically increases LZ77 token matches.
  2. Use Integer Quantization: Map floating-point values from [-1.0, 1.0] to [-100, 100] or 8-bit integers [-128, 127]. Shorter numbers yield smaller uncompressed strings and compress more densely.
  3. Separate Min/Max Channels: If rendering minimum and maximum peaks, storing them as two contiguous blocks rather than interleaving them (e.g., [min, min, ...], [max, max, ...]) creates smoother local gradients that compress slightly better than oscillating numbers.
  4. Pre-compress Static Files: Because peak data is static, generate .json.gz and .json.br files at build time using maximum compression levels (Gzip -9 or Brotli -q 11) to bypass real-time CPU overhead on the web server.
