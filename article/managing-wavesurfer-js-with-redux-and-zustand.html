Managing Wavesurfer.js with Redux and Zustand

Managing active Wavesurfer.js audio player instances across modern web applications requires coordinating complex, imperative audio objects with reactive user interfaces. This article examines how state management tools—specifically Zustand, Redux Toolkit, and React Context—can effectively register, synchronize, and clean up active Wavesurfer.js instances without degrading performance or violating architectural best practices.

The Challenge of Wavesurfer.js Instances in State Stores

Wavesurfer.js relies on an imperative lifecycle: it binds directly to a DOM node, manages Web Audio API contexts, and exposes methods like play(), pause(), and destroy().

Because a Wavesurfer instance is a complex, stateful, and non-serializable JavaScript object, placing it directly into a standard state store often introduces architectural challenges:

  • Serialization Issues: Stores designed around immutability and serializability (such as Redux) throw warnings or fail devtools time-travel features when holding raw DOM or audio instances.
  • Garbage Collection and Memory Leaks: If an instance is stored globally without an explicit call to .destroy() upon component unmounting, dangling audio nodes and event listeners persist in memory.
  • Rerender Cascades: Triggering global state updates on high-frequency events (like audioprocess or timeupdate) causes unnecessary UI re-renders if not decoupled from the main reactive tree.

Managing Instances with Zustand

Zustand is widely regarded as the most ergonomic solution for managing Wavesurfer.js instances. Because Zustand does not require stored data to be serializable, it can hold active class instances and DOM-related objects directly.

Implementation Pattern

In Zustand, you can store either a single active instance or a map of multiple instances keyed by track or player ID.

import { create } from 'zustand';

export const useAudioStore = create((set, get) => ({
  activePlayer: null,
  isPlaying: false,
  currentTime: 0,
  
  setActivePlayer: (instance) => {
    const current = get().activePlayer;
    if (current && current !== instance) {
      current.destroy();
    }
    set({ activePlayer: instance });
  },

  play: () => {
    const { activePlayer } = get();
    if (activePlayer) {
      activePlayer.play();
      set({ isPlaying: true });
    }
  },

  pause: () => {
    const { activePlayer } = get();
    if (activePlayer) {
      activePlayer.pause();
      set({ isPlaying: false });
    }
  },

  destroyPlayer: () => {
    const { activePlayer } = get();
    if (activePlayer) {
      activePlayer.destroy();
      set({ activePlayer: null, isPlaying: false, currentTime: 0 });
    }
  }
}));

Why Zustand Works Well

  • Direct Object Handling: No middleware configuration is required to bypass non-serializable checks.
  • Transient Updates: Subscribers can listen to micro-state updates without forcing complete component tree updates.
  • Outside-React Access: Wavesurfer event listeners (e.g., wavesurfer.on('ready', ...)) can call store actions directly outside the React render cycle.

Managing Instances with Redux Toolkit (RTK)

Redux strictly discourages storing non-serializable values like Wavesurfer instances in the store state. When integrating Wavesurfer.js with Redux, you have two primary architectural approaches.

Approach A: The External Instance Registry (Recommended)

The cleanest Redux pattern stores only serializable metadata (such as activeTrackId, playbackStatus, duration, and currentTime) in the Redux slice. The actual WaveSurfer objects are maintained in an external, module-scoped Map or singleton registry.

// playerRegistry.js - Non-reactive, non-serializable store
const playerRegistry = new Map();

export const registerPlayer = (id, instance) => playerRegistry.set(id, instance);
export const getPlayer = (id) => playerRegistry.get(id);
export const unregisterPlayer = (id) => {
  const player = playerRegistry.get(id);
  if (player) {
    player.destroy();
    playerRegistry.delete(id);
  }
};

Redux actions then dispatch playback intentions (e.g., playTrack(id)), and Redux middleware or custom hooks synchronize those intentions with the registry:

// Component or custom hook
const handlePlay = (trackId) => {
  dispatch(setActiveTrack(trackId));
  const player = getPlayer(trackId);
  if (player) {
    player.play();
  }
};

Approach B: Ignoring the Serializability Check

If you must store the instance directly in Redux, you must configure Redux Toolkit's middleware to ignore the state path containing the Wavesurfer instance:

import { configureStore } from '@reduxjs/toolkit';
import playerReducer from './playerSlice';

export const store = configureStore({
  reducer: {
    player: playerReducer,
  },
  middleware: (getDefaultMiddleware) =>
    getDefaultMiddleware({
      serializableCheck: {
        ignoredActions: ['player/setPlayerInstance'],
        ignoredPaths: ['player.activeInstance'],
      },
    }),
});

While functional, this approach circumvents Redux’s core guarantees and is generally less maintainable than decoupling via an instance registry.

Alternative Solutions

React Context with useRef

For applications where the audio player scope is localized to a specific route or feature, React Context combined with a useRef holding a registry map is a lightweight alternative. The Context provides reactive state (such as currentTrackId), while the ref holds the mutable Wavesurfer instances without inducing re-renders when internal player pointers change.

MobX

MobX is well-suited for Wavesurfer.js because it embraces mutable object references and fine-grained reactivity. A MobX store can declare a Wavesurfer instance as an observable property (or mark it with makeObservable and observable.ref), allowing components to react directly to player state changes without serialization overhead.

Choosing the Right Tool

  • Choose Zustand if you need a lightweight, global store that natively accommodates imperative JavaScript instances alongside reactive UI state with minimal setup.
  • Choose Redux Toolkit if your application is already heavily invested in the Redux ecosystem, utilizing an external registry module to separate audio instances from serializable store data.
  • Choose React Context + Refs if audio playback is isolated to specific component trees and does not need to persist across unmounts or page-wide navigation.
