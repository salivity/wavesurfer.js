Stop Wavesurfer Audio on SPA Router Transitions

Managing audio playback across single-page application (SPA) router transitions requires intentional teardown logic to prevent "ghost audio" caused by abandoned Wavesurfer.js instances. When users navigate between routes, the DOM element hosting the waveform unmounts, but the underlying Web Audio API context or HTML5 Audio element can remain active in memory and continue playing in the background. Resolving this issue involves using component lifecycle hooks to invoke teardown methods, leveraging global router guards for centralized cleanup, and ensuring the Web Audio context is properly closed.

The Cause of Abandoned Audio Instances

In a typical multi-page architecture, navigating to a new URL unloads the entire document, automatically stopping all audio threads and garbage-collecting media elements. In a single-page application (using React Router, Vue Router, Angular Router, etc.), navigation only swaps components within the existing DOM without reloading the browser window.

Wavesurfer.js attaches either an HTML5 HTMLAudioElement or creates a Web Audio AudioContext. If a component unmounts without explicitly calling the Wavesurfer cleanup methods, the JavaScript reference to the visual waveform may be detached, but the browser's audio processing thread continues running. This results in orphaned audio that the user can hear but no longer control via the UI.

Component-Level Lifecycle Cleanup

The most direct solution is to tie the Wavesurfer instance directly to the lifecycle of the component rendering it. Wavesurfer provides a dedicated .destroy() method that pauses playback, removes event listeners, disconnects audio nodes, and clears the container DOM.

React Implementation

In React, the cleanup phase of a useEffect hook ensures .destroy() is called whenever the component unmounts or before the effect re-runs.

import { useEffect, useRef } from 'react';
import WaveSurfer from 'wavesurfer.js';

function AudioPlayer({ audioUrl }) {
  const containerRef = useRef(null);
  const wavesurferRef = useRef(null);

  useEffect(() => {
    if (!containerRef.current) return;

    wavesurferRef.current = WaveSurfer.create({
      container: containerRef.current,
      url: audioUrl,
    });

    return () => {
      if (wavesurferRef.current) {
        wavesurferRef.current.destroy();
        wavesurferRef.current = null;
      }
    };
  }, [audioUrl]);

  return <div ref={containerRef} />;
}

Vue Implementation

In Vue 3, the onBeforeUnmount lifecycle hook guarantees that the instance is torn down before the route transition removes the component from the DOM.

<script setup>
import { ref, onMounted, onBeforeUnmount } from 'vue';
import WaveSurfer from 'wavesurfer.js';

const waveformRef = ref(null);
let wavesurfer = null;

onMounted(() => {
  wavesurfer = WaveSurfer.create({
    container: waveformRef.value,
    url: '/media/track.mp3',
  });
});

onBeforeUnmount(() => {
  if (wavesurfer) {
    wavesurfer.destroy();
    wavesurfer = null;
  }
});
</script>

<template>
  <div ref="waveformRef"></div>
</template>

Global Router Navigation Guards

Relying entirely on component lifecycles can fail if async transitions delay unmounting, or if transitions abort mid-flight. A centralized approach using router middleware or global navigation guards guarantees that audio cannot leak across view changes.

Centralized Audio Registry Pattern

Create an audio management singleton that tracks active Wavesurfer instances across the entire application:

class AudioManager {
  constructor() {
    this.activeInstance = null;
  }

  register(instance) {
    if (this.activeInstance && this.activeInstance !== instance) {
      this.stop();
    }
    this.activeInstance = instance;
  }

  stop() {
    if (this.activeInstance) {
      this.activeInstance.destroy();
      this.activeInstance = null;
    }
  }
}

export const audioManager = new AudioManager();

Hooking into the Router

Connect the registry to the router’s navigation events. For example, in Vue Router:

import { createRouter, createWebHistory } from 'vue-router';
import { audioManager } from './audioManager';

const router = createRouter({
  history: createWebHistory(),
  routes: [...],
});

router.beforeEach((to, from, next) => {
  audioManager.stop();
  next();
});

For React Router (v6+), a top-level route listener accomplishes the same:

import { useEffect } from 'react';
import { useLocation } from 'react-router-dom';
import { audioManager } from './audioManager';

export function RouteAudioWatcher() {
  const location = useLocation();

  useEffect(() => {
    audioManager.stop();
  }, [location.pathname]);

  return null;
}

Web Audio Context Handling

When Wavesurfer.js is configured with the Web Audio backend (backend: 'WebAudio'), modern browsers impose limits on the total number of concurrent AudioContext instances (typically 6 to 32 depending on the browser). Failing to release instances leads to memory leaks and will eventually throw an error: The AudioContext was not allowed to start or Max dynamic audio contexts reached.

Calling wavesurfer.destroy() automatically closes the associated AudioContext in current versions of Wavesurfer.js. If you are passing a pre-existing custom audioContext to the configuration, Wavesurfer will not close it automatically. In that scenario, you must handle the closure manually:

if (customAudioContext && customAudioContext.state !== 'closed') {
  customAudioContext.close();
}

Handling In-Flight Asset Requests

If a user navigates away while an audio file is actively loading or decoding, Wavesurfer may attempt to play after the route transition finishes. To prevent this race condition:

  1. Use an AbortController signal when fetching custom audio buffers and abort it during the cleanup lifecycle.
  2. Ensure .destroy() is called even if the ready or decode events have not yet fired. Calling destroy() on an initializing Wavesurfer instance cancels internal download tasks and prevents orphaned playback triggers.
