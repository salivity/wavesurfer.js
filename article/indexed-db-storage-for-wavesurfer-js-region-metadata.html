IndexedDB Storage for Wavesurfer.js Region Metadata

Building offline-capable audio applications with Wavesurfer.js requires a structured client-side database to persist audio annotations and user-generated boundaries. This article outlines the optimal IndexedDB object store schemas, key paths, and indexing strategies used to store, query, and synchronize offline region metadata generated by the Wavesurfer.js Regions plugin.

The Role of IndexedDB in Audio Annotation

The Wavesurfer.js Regions plugin allows users to create visual overlays on waveforms representing audio segments. Each region generates critical runtime properties such as start time, end time, unique identifiers, and custom metadata. Because this data exists only in browser memory, IndexedDB serves as the persistent offline layer, ensuring that annotations survive page reloads and network disconnects.

Core Object Store Schemas

To manage regions efficiently, IndexedDB should use a dedicated database (e.g., AudioWorkspaceDB) with at least two primary object stores: one for the audio track records and one for the region metadata.

1. The regions Object Store

The regions store houses the individual audio segment definitions.

  • Primary Key / keyPath: Set to "id". This directly maps to the region.id generated by Wavesurfer.js (usually a string like wavesurfer_xxxxxx or a UUID).
  • Auto-increment: false (Wavesurfer handles ID generation).

A standard region record stored in this object store includes:

{
  "id": "region_1711904500_abc123",
  "trackId": "track_402",
  "start": 12.45,
  "end": 25.80,
  "color": "rgba(0, 255, 0, 0.3)",
  "data": {
    "label": "Chorus",
    "notes": "Lead vocal entry"
  },
  "attributes": {
    "drag": true,
    "resize": true
  },
  "updatedAt": 1711904500000,
  "syncStatus": "synced"
}

2. Essential Indexes for the regions Store

To support fast queries and offline synchronization, the regions store requires three primary indexes:

  • trackId Index (trackId, { unique: false }): Allows rapid retrieval of all regions associated with a specific audio asset using an IndexedDB cursor or getAll() call when a new waveform is loaded.
  • start Index (start, { unique: false }): Enables temporal sorting. Fetching regions ordered by their appearance in the timeline eliminates the need for expensive in-memory sorting operations prior to rendering.
  • syncStatus Index (syncStatus, { unique: false }): Tracks offline state changes. Values like "pending_creation", "pending_update", or "pending_deletion" allow background workers to identify and upload changes once connectivity returns.

Handling Offline Deletions: Tombstone Stores

When working offline, deleting a region from IndexedDB cannot simply execute an objectStore.delete(id) operation if those changes must eventually sync to a remote server. Instead, two patterns are commonly used:

  1. Soft Deletes in the Main Store: Set a boolean flag (isDeleted: true) and update syncStatus to "pending_deletion". Filter these records out when calling regionsPlugin.addRegion().
  2. A Dedicated deleted_regions Store: Move deleted region identifiers and their associated trackId into a lightweight tombstone store. This keeps the primary regions store clean and performant for active playback queries while maintaining a dedicated queue for sync processes.

Event-Driven Synchronization Workflow

Connecting Wavesurfer.js events directly to IndexedDB transactions ensures transactional integrity between the visual waveform and local persistence:

  • Load Phase: Query the trackId index on database initialization. Iterate through the results and invoke wsRegions.addRegion(regionData) for each entry.
  • Create / Update Phases: Listen to the region-created and region-updated events emitted by the Wavesurfer instance. Extract the properties and execute a readwrite transaction using objectStore.put(regionPayload) to persist state changes instantly.
  • Remove Phase: Listen to the region-removed event, updating the syncStatus or relocating the ID to the tombstone store within a readwrite transaction.
