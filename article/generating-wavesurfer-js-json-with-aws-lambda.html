Generating Wavesurfer.js JSON with AWS Lambda

This article outlines how to build automated, serverless workflows using AWS Lambda or Google Cloud Functions to process audio files into pre-computed JSON peak data for Wavesurfer.js. Rendering waveforms directly in the browser requires downloading and decoding entire audio files via the Web Audio API, which degrades frontend performance for long tracks. By moving this computation to serverless cloud triggers using utilities like audiowaveform, you can generate lightweight JSON peak data that loads instantly on the client side.

The Serverless Waveform Processing Concept

Wavesurfer.js accepts pre-rendered peak arrays through its peaks option, bypassing the browser's need to decode the underlying audio file. To generate this data automatically in the cloud, serverless architectures rely on an event-driven storage trigger, a containerized audio analysis tool (most commonly BBC’s open-source audiowaveform binary), and an output target for the resulting JSON.

AWS Lambda Workflow

The standard AWS workflow uses Amazon S3, AWS Lambda, and an S3 output bucket or CloudFront distribution.

  1. Storage Trigger: A user or backend uploads an audio file (MP3, WAV, FLAC, AAC) to an Amazon S3 input bucket. This triggers an s3:ObjectCreated:* event notification.
  2. Lambda Execution Environment: Because standard Lambda runtimes lack audio processing utilities, the Lambda function must either include a custom Lambda Layer containing the statically compiled audiowaveform binary or run as a container image defined via Dockerfile based on public.ecr.aws/lambda/nodejs or public.ecr.aws/lambda/python.
  3. Execution Steps:

    • The Lambda function downloads the audio file from S3 into the /tmp ephemeral storage directory.

    • A child process executes audiowaveform:

      audiowaveform -i /tmp/audio.mp3 -o /tmp/peaks.json --pixels-per-second 20 --bits 8

    • The binary extracts peak amplitude data and formats it directly into JSON containing an array of integers representing min/max values.

    • The Lambda script uploads peaks.json to a designated S3 output bucket with appropriate caching headers (Cache-Control) and CORS settings.

  4. Cleanup: Temporary files in /tmp are removed to prevent storage exhaustion on warm Lambda container re-use.

Google Cloud Functions Workflow

The workflow on Google Cloud Platform functions similarly using Cloud Storage and Cloud Functions (2nd Gen).

  1. Cloud Storage Trigger: An audio file lands in a Google Cloud Storage (GCS) bucket, triggering an Eventarc event or Cloud Storage google.cloud.storage.object.v1.finalized trigger.
  2. Function Environment: Cloud Functions (2nd Gen) run on Cloud Run instances. This allows developers to use Dockerfiles or buildpacks that install audiowaveform and ffmpeg via package managers like apt-get directly into the runtime environment.
  3. Processing and Storage: The function streams or downloads the file to memory or the /tmp directory, runs audiowaveform to export the JSON, and writes the JSON file back to GCS adjacent to the source audio or in a dedicated metadata bucket.

Consuming the Output in Wavesurfer.js

Once the JSON file is generated and stored, the frontend client requests both the audio file and its corresponding JSON representation. The Wavesurfer.js instance is initialized by supplying the pre-computed peak data directly:

fetch('https://cdn.example.com/audio/track-123.json')
  .then(response => response.json())
  .then(data => {
    const wavesurfer = WaveSurfer.create({
      container: '#waveform',
      waveColor: '#4F46E5',
      progressColor: '#818CF8',
      peaks: data.data,
      duration: data.length / data.sample_rate
    });
    
    wavesurfer.load('https://cdn.example.com/audio/track-123.mp3');
  });

Using this architecture, waveform visualization appears instantly without blocking the browser thread, while compute costs remain strictly pay-per-use based on the duration of the serverless function execution.
