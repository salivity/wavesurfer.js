How to Add Bearer Auth Headers in Wavesurfer.js

Securing audio resources behind protected API endpoints requires attaching authentication credentials to outgoing network calls. In modern versions of Wavesurfer.js (v7+), audio files are retrieved using the native Fetch API rather than legacy XMLHttpRequest objects. This article explains how to attach dynamic Bearer authentication tokens to Wavesurfer.js audio requests using the built-in fetchParams option, how to update these headers dynamically between loads, and how to use custom fetch implementations with blobs for complete control over token life cycles.

Using the fetchParams Option

Wavesurfer.js accepts a fetchParams property within its configuration object. This property mirrors standard Fetch API options (RequestInit), allowing you to pass custom headers, HTTP methods, or credentials directly to the internal fetch call:

import WaveSurfer from 'wavesurfer.js';

const token = 'YOUR_BEARER_TOKEN';

const wavesurfer = WaveSurfer.create({
  container: '#waveform',
  waveColor: '#4F4A85',
  progressColor: '#383351',
  url: 'https://api.example.com/audio/track-123.mp3',
  fetchParams: {
    headers: {
      Authorization: `Bearer ${token}`,
    },
  },
});

Updating Headers Dynamically for New Tracks

If your application loads new tracks dynamically or uses short-lived tokens that must be refreshed before a request occurs, you can update fetchParams directly on the instance's options object prior to invoking load():

async function loadProtectedAudio(wavesurfer, audioUrl) {
  // Retrieve a fresh token (e.g., from an auth provider or storage)
  const freshToken = await getValidAuthToken();

  // Update fetchParams on the existing instance
  wavesurfer.options.fetchParams = {
    headers: {
      Authorization: `Bearer ${freshToken}`,
      Accept: 'audio/*',
    },
  };

  // Trigger the load request with updated headers
  wavesurfer.load(audioUrl);
}

Alternative Approach: Custom Fetch with loadBlob()

For complex authentication architectures—such as automatic retry logic, interceptors, or 401 handling—the most robust approach is fetching the audio manually using the native window.fetch() function, converting the response into a Blob, and passing it to Wavesurfer:

async function fetchAndRenderAudio(wavesurfer, audioUrl) {
  const token = await getValidAuthToken();

  const response = await fetch(audioUrl, {
    method: 'GET',
    headers: {
      Authorization: `Bearer ${token}`,
    },
  });

  if (!response.ok) {
    throw new Error(`Failed to load audio: ${response.statusText}`);
  }

  const audioBlob = await response.blob();
  wavesurfer.loadBlob(audioBlob);
}

This pattern isolates Wavesurfer from network management and authentication logic, ensuring audio rendering begins only after a valid payload has been retrieved.

Legacy Configuration (Wavesurfer.js v6 and Earlier)

In Wavesurfer.js v6 and below, requests relied on XMLHttpRequest. For older versions, headers must be specified via the xhr configuration property:

const wavesurfer = WaveSurfer.create({
  container: '#waveform',
  xhr: {
    requestHeaders: [
      {
        key: 'Authorization',
        value: `Bearer ${token}`,
      },
    ],
  },
});
