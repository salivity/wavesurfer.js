Fix Wavesurfer.js Playhead Desync in Background Tabs

When a browser tab loses focus, aggressive throttling suspends requestAnimationFrame loops to conserve battery and CPU resources. Because the underlying HTML5 audio element or Web Audio context continues to play in the background, Wavesurfer.js stops updating its visual canvas, resulting in a frozen or desynchronized playhead when the user returns. This guide explains why this desynchronization occurs and details actionable solutions—ranging from the visibilitychange API to Web Workers—to keep the audio and visualization aligned.

Why Background Throttling Breaks Wavesurfer.js

Modern web browsers drop requestAnimationFrame execution to zero frames per second for hidden tabs. Wavesurfer.js uses animation frames to drive smooth continuous rendering of the progress bar, playhead, and cursor across the waveform canvas.

While the rendering loop halts entirely, the browser's audio thread runs unimpeded to ensure uninterrupted playback. When the user switches back to the tab, the visual playhead either stays stuck at the point where the tab was hidden, snaps violently, or drifts out of sync because delta calculations accumulated incorrectly during the pause.

Solution 1: Resynchronize on Visibility Change

The cleanest and most resource-efficient approach is to force Wavesurfer.js to resynchronize its visual state as soon as the user returns to the tab. You can achieve this by listening to the Page Visibility API's visibilitychange event.

When the document becomes visible again, query the exact currentTime from the audio source and tell Wavesurfer.js to re-render:

document.addEventListener('visibilitychange', () => {
  if (!document.hidden && wavesurfer.isPlaying()) {
    // Retrieve the exact current playback time
    const currentTime = wavesurfer.getCurrentTime();
    
    // Force Wavesurfer to seek/redraw at the current time without interrupting audio
    wavesurfer.setTime(currentTime);
  }
});

In Wavesurfer.js v7, rendering is internally tied closely to media element events. Calling setTime() updates the internal visual progress calculation immediately, clearing out any frame delta lag accumulated during the freeze.

Solution 2: Fall Back to timeupdate Events

If you rely on continuous custom tracking (such as displaying real-time transcripts, scrolling waveforms, or external playheads), do not depend purely on request animation loops. HTML5 <audio> elements continue firing standard timeupdate events even when backgrounded (typically around 3 to 4 times per second).

Configure Wavesurfer to bind critical state changes to timeupdate:

wavesurfer.on('timeupdate', (currentTime) => {
  if (document.hidden) {
    // Keep low-frequency internal counters updated in the background
    updateExternalPlayheadTracker(currentTime);
  }
});

Solution 3: Offload Timers to a Web Worker

If your application requires continuous, real-time visual synchronization even in background tabs (for example, picture-in-picture mode or audio processing graphs), main-thread timers (setInterval, setTimeout, and requestAnimationFrame) will not suffice.

Browsers do not throttle Web Workers as aggressively as main-thread UI rendering loops. You can implement a worker-based timer to keep interval ticks constant:

  1. Create an inline Web Worker that runs a non-throttled interval loop.
  2. Post a message to the main thread on every tick.
  3. Update the playhead programmatically.
// worker-timer.js
const workerBlob = new Blob([`
  let intervalId;
  self.onmessage = function(e) {
    if (e.data === 'start') {
      intervalId = setInterval(() => postMessage('tick'), 100);
    } else if (e.data === 'stop') {
      clearInterval(intervalId);
    }
  };
`], { type: 'application/javascript' });

const timerWorker = new Worker(URL.createObjectURL(workerBlob));

// Listen for playback events
wavesurfer.on('play', () => timerWorker.postMessage('start'));
wavesurfer.on('pause', () => timerWorker.postMessage('stop'));
wavesurfer.on('finish', () => timerWorker.postMessage('stop'));

timerWorker.onmessage = () => {
  if (document.hidden && wavesurfer.isPlaying()) {
    // Keep progress synchronized across custom background tasks
    const currentProgress = wavesurfer.getCurrentTime() / wavesurfer.getDuration();
    wavesurfer.drawer.progress(currentProgress);
  }
};

Summary of Best Practices

  • For basic playback and visual waveforms, use the visibilitychange API to snap the playhead back to the accurate audio position when the user refocuses the tab.
  • Avoid calculating continuous playback state manually using elapsed frame deltas; always read directly from wavesurfer.getCurrentTime() or the underlying mediaElement.currentTime.
  • If persistent background updates are strictly required, bypass main-thread throttling via Web Workers.
