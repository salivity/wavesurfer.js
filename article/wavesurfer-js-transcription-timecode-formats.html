Wavesurfer.js Transcription Timecode Formats

Building a transcription application with Wavesurfer.js requires handling timecodes in two distinct contexts: the internal numeric format required by the audio engine and the formatted strings required for user display and file export. This guide details the exact timecode structures Wavesurfer.js expects, standard export formats such as WebVTT and SRT, and the conversion methods needed to keep your audio playback and transcript synchronized.

Internal Format: Floating-Point Seconds

Internally, Wavesurfer.js handles all time references strictly as floating-point numbers representing seconds. Whether you are tracking the current playback position, seeking, or creating text segments using the Regions plugin (wavesurfer.js/dist/plugins/regions.esm.js), the engine expects numeric seconds rather than formatted time strings.

When defining segments or words for transcription, your data models should store timecodes as numbers:

const segment = {
  id: "segment-1",
  start: 14.25, // 14 seconds and 250 milliseconds
  end: 18.8,    // 18 seconds and 800 milliseconds
  text: "Welcome to this transcription demonstration."
};

// Creating a synchronized region in Wavesurfer.js
wsRegions.addRegion({
  start: segment.start,
  end: segment.end,
  content: segment.text,
  color: 'rgba(0, 123, 255, 0.2)'
});

Using numeric values ensures precise calculations, smooth timeline scrubbing, and optimal performance when querying timestamps during playback events like timeupdate.

External Formats: WebVTT and SRT

While the player requires seconds, transcription workflows rely on industry-standard subtitle formats for importing, exporting, and displaying text.

  • WebVTT (.vtt): Uses the format HH:MM:SS.mmm or MM:SS.mmm (hours, minutes, seconds, milliseconds separated by a period).
    • Example: 00:01:24.500
  • SubRip (.srt): Uses the format HH:MM:SS,mmm (hours, minutes, seconds, milliseconds separated by a comma).
    • Example: 00:01:24,500

Parsing and Formatting Timecodes

To integrate these standard formats with Wavesurfer.js, you must implement bidirectional conversion functions.

Converting Strings to Seconds (Import)

When loading a WebVTT or SRT file into Wavesurfer.js, convert the timestamp strings into total seconds:

function timecodeToSeconds(timecode) {
  // Normalize commas to periods to handle both SRT and VTT
  const normalized = timecode.replace(',', '.');
  const parts = normalized.split(':').map(parseFloat);

  if (parts.length === 3) {
    return parts[0] * 3600 + parts[1] * 60 + parts[2];
  } else if (parts.length === 2) {
    return parts[0] * 60 + parts[1];
  }
  return 0;
}

Converting Seconds to Strings (Display and Export)

When presenting time to users or exporting the completed transcript, convert the player’s floating-point seconds back into a formatted timecode:

function secondsToTimecode(totalSeconds, format = 'vtt') {
  const hours = Math.floor(totalSeconds / 3600);
  const minutes = Math.floor((totalSeconds % 3600) / 60);
  const seconds = Math.floor(totalSeconds % 60);
  const milliseconds = Math.floor((totalSeconds % 1) * 1000);

  const pad = (num, size = 2) => String(num).padStart(size, '0');
  const separator = format === 'srt' ? ',' : '.';

  return `${pad(hours)}:${pad(minutes)}:${pad(seconds)}${separator}${pad(milliseconds, 3)}`;
}

Best Practices for Transcription Apps

  1. Maintain Millisecond Precision: Store timecodes with at least three decimal places (e.g., 12.345). Rounding to whole seconds degrades synchronization, causing text highlights to feel delayed.
  2. Isolate State from Presentation: Keep your application state in raw numeric seconds. Only run the formatting functions at the UI layer or during export generation.
  3. Handle Floating-Point Drift: When editing boundaries visually with the Regions plugin, apply Math.round(val * 1000) / 1000 to prevent JavaScript floating-point arithmetic artifacts (such as 14.250000000000002).
