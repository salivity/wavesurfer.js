Build an Offline Mobile Audio Editor with Wavesurfer.js

Building an offline-first mobile web audio editor requires combining modern browser storage, progressive web app (PWA) architecture, and efficient client-side audio processing. By leveraging Wavesurfer.js for visual rendering alongside the native Web Audio API and IndexedDB, you can deliver a responsive, touch-optimized workstation that functions reliably without an active internet connection.

1. Establish the Offline PWA Foundation

To make the application functional offline, it must be structured as a Progressive Web App (PWA). Register a Service Worker to pre-cache the application shell, including HTML, CSS, JavaScript bundles, and the Wavesurfer.js library itself.

Use a Cache-First strategy for application assets. This guarantees that on subsequent visits, even when the mobile device has intermittent or zero network access, the UI and audio engine load instantly.

2. Manage Audio Storage with IndexedDB

Mobile devices frequently close background tabs or reload pages to free memory, making persistent client-side storage essential. Use IndexedDB to store raw audio data as binary Blob or ArrayBuffer objects rather than relying on localStorage (which is synchronous and has strict size limits).

Create an object store for audio tracks and project metadata. When a user imports an audio file via an <input type="file" accept="audio/*"> element, write the raw binary directly to IndexedDB. When reopening the editor, retrieve the stored buffer and feed it directly into your audio pipeline.

3. Configure Wavesurfer.js for Mobile Screens

Mobile screens present limited horizontal canvas space and processing constraints. Initialize Wavesurfer.js with settings optimized for touch and performance:

import WaveSurfer from 'wavesurfer.js';
import RegionsPlugin from 'wavesurfer.js/dist/plugins/regions.esm.js';

const ws = WaveSurfer.create({
  container: '#waveform',
  waveColor: '#4F46E5',
  progressColor: '#818CF8',
  cursorColor: '#FFFFFF',
  barWidth: 2,
  barGap: 1,
  responsive: true,
  height: 120,
  plugins: [
    RegionsPlugin.create()
  ]
});

Keep barWidth set to a minimum of 2 pixels to reduce the total number of canvas render paths, which conserves CPU and battery on mobile devices. Enable responsive rendering so the waveform recalculates its dimensions during device orientation changes.

4. Implement Non-Destructive Audio Editing

Wavesurfer.js excels at visualization and playback control, but actual editing operations—such as trimming, splitting, and splicing—are handled using the browser's native AudioContext.

  1. Decoding: Use AudioContext.decodeAudioData() to transform the stored ArrayBuffer into an AudioBuffer.
  2. Region Selection: Use the Wavesurfer Regions plugin to allow users to drag selection handles over the waveform to mark start and end points. Ensure drag handles have sufficient touch target size (at least 48x48 pixels) via CSS.
  3. Buffer Manipulation: To crop audio, create a new AudioBuffer with the desired duration. Copy channel data from the original buffer to the new buffer using copyFromChannel and copyToChannel.
  4. Update Visualization: Load the newly sliced AudioBuffer directly back into Wavesurfer via ws.loadAudioBuffer(newBuffer) and update the record in IndexedDB.

5. Offload Encoding to Web Workers

Exporting audio back to formats such as WAV or MP3 requires computationally intensive encoding. Executing this on the main JavaScript thread will cause the mobile UI to stutter or crash.

Delegate encoding tasks to a dedicated Web Worker. When the user taps "Export," pass the raw PCM float arrays to the worker, encode the audio into a standard file format, and return a downloadable Blob. This keeps the waveform scrolling and user interface smooth throughout processing.
