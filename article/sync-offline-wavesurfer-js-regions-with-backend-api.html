Sync Offline Wavesurfer.js Regions with Backend API

This article explains how to reliably reconcile offline audio region edits made using the Wavesurfer.js Regions plugin with a backend database once network connectivity is restored. It outlines the architecture needed to intercept client-side audio annotation events, persist changes locally in an append-only mutation queue, resolve conflicts, and batch synchronize state with your remote API.

Local Mutation Tracking

To prevent data loss when a user modifies regions offline, avoid relying purely on Wavesurfer.js internal state. Instead, intercept all region lifecycle events and store them in an IndexedDB store or a persistent localStorage queue.

Wavesurfer.js provides lifecycle events such as region-created, region-updated, and region-clicked (often used to trigger deletion). When these events fire while navigator.onLine is false or when network requests fail, serialize the region's properties (id, start, end, color, and any custom data attributes) into a mutation record.

Each mutation entry should contain:

  • A client-generated UUID for the region.
  • The mutation type (CREATE, UPDATE, or DELETE).
  • A high-resolution UTC timestamp.
  • A local revision or version counter.

Handling Temporary Identifiers

When users create regions offline, the backend database has not yet generated an auto-incrementing ID or primary key. To handle this:

  1. Assign every region a client-side UUID (e.g., using crypto.randomUUID()) upon creation in Wavesurfer.js.
  2. Maintain this UUID as a distinct property, such as client_id, in both your frontend data and backend database schemas.
  3. If your database uses a separate internal primary key (like a relational integer ID), ensure subsequent UPDATE or DELETE mutations in the offline queue reference the client_id until the server provides the mapped database ID.

Detecting Network Recovery

Do not rely solely on the browser's window.addEventListener('online') event, as it only indicates connection to a local network, not necessarily internet access or server availability.

Implement a dual-check mechanism:

  1. Listen for the online event to trigger an immediate connectivity check.
  2. Execute an HTTP HEAD or lightweight health-check request to your API to verify actual reachability.
  3. Alternatively, leverage the service worker SyncManager API (periodicSync or sync) for background processing if the user closes the tab before reconnection.

Conflict Resolution Strategies

When multiple clients edit the same audio regions offline, or if edits occurred on the server while the client was disconnected, conflicts will arise. Select one of two primary resolution strategies:

  • Last-Write-Wins (LWW): Compare the timestamp of the incoming offline mutation with the updated_at column in the database. If the mutation's timestamp is newer, overwrite the record; otherwise, discard the offline edit and return the server's current state to the client.
  • Vector Clocks / Version Numbers: Store an integer version field on both the region object and database row. If a client attempts to update version 2, but the database is already at version 3, reject the direct overwrite. The client must then fetch the current server state, prompt the user or apply automated merge logic, and submit a resolved version 4.

Synchronization Pipeline

Once the connection is verified, process the mutation queue through a dedicated batch endpoint (POST /api/regions/reconcile):

  1. Batching: Send all queued actions in a single payload rather than firing multiple atomic requests. This minimizes network overhead and allows the server to wrap all changes in a single database transaction.
  2. Atomic Execution: The backend processes mutations sequentially according to their client timestamps. It inserts new regions, updates modified boundaries, removes deleted IDs, and resolves conflicts.
  3. Response and Re-indexing: The server returns the final canonical region state, including database IDs and updated version numbers.
  4. Client State Update: Clear the local mutation queue upon a 200 OK response. Update the in-memory Wavesurfer.js regions using wavesurfer.plugins.regions.clear() followed by wavesurfer.plugins.regions.addRegion() with the canonical server data, ensuring UI state matches the backend source of truth.
