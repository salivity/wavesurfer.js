Handling HTTP Status in Wavesurfer.js Audio Fetch

Handling HTTP status codes effectively during audio retrieval in Wavesurfer.js is critical for building resilient web audio applications. While Wavesurfer provides default methods for fetching and decoding audio, developers frequently require granular control over responses like 401 Unauthorized, 403 Forbidden, 404 Not Found, or 500 Internal Server Error. This article covers the available strategies for implementing custom HTTP status handling in Wavesurfer.js, ranging from using the Fetch API with loadBlob to utilizing built-in fetch parameters and error events.

1. Manual Fetch API with loadBlob()

The most versatile method for handling specific HTTP status codes is decoupling the network request from Wavesurfer's internal loading pipeline. By fetching the audio file explicitly using the native fetch() API, you gain direct access to the Response object before passing data to Wavesurfer.

async function loadAudioWithCustomHandling(url, wavesurfer) {
  try {
    const response = await fetch(url, {
      headers: {
        'Authorization': 'Bearer ' + userToken,
      },
    });

    switch (response.status) {
      case 200:
      case 206: // Partial Content for range requests
        const audioBlob = await response.blob();
        await wavesurfer.loadBlob(audioBlob);
        break;

      case 401:
        // Handle token expiration or unauthorized access
        await refreshAuthToken();
        return loadAudioWithCustomHandling(url, wavesurfer);

      case 403:
        console.error('Access denied to audio asset.');
        displayErrorUI('You do not have permission to play this track.');
        break;

      case 404:
        console.error('Audio file not found.');
        displayErrorUI('The requested audio track does not exist.');
        break;

      case 500:
      case 502:
      case 503:
        console.error('Server error encountered.');
        retryWithBackoff(url, wavesurfer);
        break;

      default:
        throw new Error(`Unhandled HTTP status: ${response.status}`);
    }
  } catch (error) {
    console.error('Network or decoding error:', error);
  }
}

This approach allows you to inspect headers, evaluate status codes, trigger authentication refreshes, or display context-specific UI notifications before any decoding attempts occur.

2. Using Wavesurfer v7 fetchParams with Error Events

In Wavesurfer.js version 7, the core library uses fetch() internally when calling wavesurfer.load(url). You can pass a standard RequestInit configuration object to fetchParams to customize request headers, credentials, and cache behavior.

While fetchParams modifies the outgoing request, handling failed statuses relies on Wavesurfer's 'error' event:

const wavesurfer = WaveSurfer.create({
  container: '#waveform',
  waveColor: '#4F46E5',
  progressColor: '#818CF8',
  fetchParams: {
    mode: 'cors',
    headers: {
      'Authorization': 'Bearer ' + userToken,
    },
  },
});

wavesurfer.on('error', (error) => {
  // Wavesurfer throws a generic error on non-2xx responses
  console.error('Wavesurfer failed to fetch or decode:', error.message);
});

wavesurfer.load('https://example.com/audio.mp3');

Note that Wavesurfer's internal loader throws a standard error when a network request fails or returns an invalid status, but it does not expose the full HTTP response object inside the 'error' callback. If detailed status inspection is required, the manual fetch approach is preferred.

3. Custom XMLHttpRequest (Legacy Wavesurfer v6 and Below)

In older versions of Wavesurfer.js (v6 and earlier), network requests were typically managed via XMLHttpRequest (XHR) instead of fetch. You could configure request parameters and hook into XHR status events through the xhr option:

const wavesurfer = WaveSurfer.create({
  container: '#waveform',
  xhr: {
    headers: [
      { key: 'Authorization', value: 'Bearer ' + userToken }
    ],
    withCredentials: true,
  },
});

wavesurfer.on('error', (err) => {
  console.error('Error during audio processing:', err);
});

wavesurfer.load('https://example.com/audio.mp3');

For advanced HTTP status handling in legacy versions, developers frequently used xhr.onreadystatechange directly within a custom loader script, parsing xhr.status manually before calling wavesurfer.loadArrayBuffer(buffer) or wavesurfer.loadBlob(blob).

Summary of Recommendations

  • Fine-grained status handling (401, 403, 404, 5xx): Fetch the asset manually via fetch(), evaluate response.status, and pass the resolved audio payload to wavesurfer.loadBlob().
  • Standard authenticated requests: Use fetchParams directly in wavesurfer.load() if you only need custom headers and can rely on generic error fallback listeners.
