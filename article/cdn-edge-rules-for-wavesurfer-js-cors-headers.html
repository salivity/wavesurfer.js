CDN Edge Rules for Wavesurfer.js CORS Headers

Wavesurfer.js renders visual audio waveforms in the browser using the Web Audio API or HTML5 Canvas, both of which require direct access to raw audio data. When audio assets are hosted on a separate domain or Content Delivery Network (CDN), browsers block the fetch request unless appropriate Cross-Origin Resource Sharing (CORS) headers are present. This article explains how CDN edge rules intercept requests to append Access-Control-Allow-Origin headers dynamically, resolving origin blocks without modifying the underlying storage layer.

Why Wavesurfer.js Requires Explicit CORS Headers

To draw peaks, calculate durations, and decode audio buffers, Wavesurfer.js relies on fetch or XMLHttpRequest along with AudioContext.decodeAudioData(). Unlike a standard <audio> tag that simply plays media, extracting raw audio byte data is subject to the browser's Same-Origin Policy.

If the audio file resides on an Amazon S3 bucket, Google Cloud Storage, or a third-party CDN domain that does not return proper CORS headers, the browser will throw an error such as:

Access to fetch at 'https://cdn.example.com/audio.mp3' from origin 'https://example.com' has been blocked by CORS policy.

While CORS can sometimes be configured directly on origin storage, applying these policies at the CDN edge provides lower latency, centralized control, and the ability to serve different origins dynamically.

How CDN Edge Rules Process Headers

CDNs operate a distributed network of edge nodes located between the end user and the origin server. Edge rules allow administrators to hook into the HTTP request and response lifecycle:

  1. Viewer Request: The browser sends an HTTP GET or preflight OPTIONS request for an audio asset, including an Origin header (e.g., Origin: https://example.com).
  2. Origin Request/Cache Check: The CDN checks its local cache. If the asset is missing, it fetches the file from the origin.
  3. Origin Response: The origin returns the file, often without CORS headers.
  4. Viewer Response (Edge Rule Execution): Before delivering the payload to the browser, the CDN edge applies rules to append custom HTTP headers to the response payload.

By injecting the headers during the Viewer Response phase, the edge server guarantees that the browser receives valid permission tokens regardless of whether the file was served from cache or fetched fresh from the origin.

Essential CORS Headers for Audio Playback

For Wavesurfer.js to function correctly, a CDN edge rule must inject more than just the primary origin header. Media loading often involves partial content loading (byte-range requests) and preflight negotiations.

  • Access-Control-Allow-Origin: Specifies permitted origins. It can be set to a wildcard (*) for public files, or configured to dynamically reflect the incoming Origin header for restricted assets.
  • Access-Control-Allow-Methods: Must allow GET, HEAD, and OPTIONS.
  • Access-Control-Allow-Headers: Must permit Range, Accept, and any custom client-side headers. Wavesurfer.js frequently relies on Range headers to stream or scrub audio.
  • Access-Control-Expose-Headers: Must expose Content-Range, Accept-Ranges, and Content-Length. Browsers require access to these headers to calculate total audio duration and manage buffer chunks properly.

Configuring Edge Rules

The configuration process varies slightly across CDN providers, but the fundamental logic remains uniform: match the incoming media request and append the required response headers.

Cloudflare Transform Rules

  1. Navigate to Rules > Transform Rules > Modify Response Header.
  2. Define an expression to match audio requests, such as http.request.uri.path.extension in {"mp3" "wav" "ogg" "flac"}.
  3. Select Set Dynamic or Set Static.
  4. Set the header name to Access-Control-Allow-Origin and define the value (e.g., * or http.request.headers["origin"][0]).
  5. Add supplemental rows for Access-Control-Allow-Headers: Range and Access-Control-Expose-Headers: Content-Range, Content-Length, Accept-Ranges.

AWS CloudFront (Response Headers Policies)

  1. In CloudFront, navigate to Policies > Response headers and click Create response headers policy.
  2. Under the Cross-origin resource sharing (CORS) section, enable CORS.
  3. Set Access-Control-Allow-Origin to your application domain or *.
  4. Check Origin override so CloudFront applies the header even if the S3 bucket does not supply one.
  5. Add Range to Access-Control-Allow-Headers and Content-Range, Content-Length, Accept-Ranges to Access-Control-Expose-Headers.
  6. Attach this policy to the CloudFront Cache Behavior governing your media path.

Fastly (VCL)

In your Fastly VCL file, append the headers during the vcl_deliver stage:

sub vcl_deliver {
  # Fastly deliver logic
  if (req.url ~ "\.(mp3|wav|ogg|flac)($|\?)") {
    set resp.http.Access-Control-Allow-Origin = "*";
    set resp.http.Access-Control-Allow-Methods = "GET, HEAD, OPTIONS";
    set resp.http.Access-Control-Allow-Headers = "Range, Content-Type";
    set resp.http.Access-Control-Expose-Headers = "Content-Range, Content-Length, Accept-Ranges";
  }
}

Handling Edge Preflight Requests (OPTIONS)

When Wavesurfer.js sends complex requests with custom headers or methods, the browser sends an HTTP OPTIONS preflight request prior to loading the media file.

To prevent origin latency or potential 403/405 errors from static storage buckets that do not recognize OPTIONS methods, configure your CDN edge rule to terminate OPTIONS calls at the edge. The edge rule should respond directly with an HTTP status 200 or 204, along with the defined CORS headers and an Access-Control-Max-Age header (e.g., 86400) to instruct the browser to cache preflight decisions for 24 hours.
