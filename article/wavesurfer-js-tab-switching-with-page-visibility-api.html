Wavesurfer.js Tab Switching with Page Visibility API

This guide explains how to manage audio playback and resource usage in Wavesurfer.js when a user switches browser tabs. By integrating the native Page Visibility API with Wavesurfer.js methods, you can automatically pause audio when a tab loses focus, restore playback when the user returns, and avoid common background throttling issues caused by modern web browsers.

The Challenge with Background Tabs

Modern browsers aggressively throttle background tabs to conserve CPU and battery life. Timers such as requestAnimationFrame and setTimeout are deprioritized or halted entirely. Since Wavesurfer.js relies on these mechanisms to draw the waveform cursor and keep the audio playback synchronized with the UI, switching tabs can lead to UI desynchronization, audio stutter, or unintended background playback.

Using the Page Visibility API provides a reliable way to detect tab state changes and control Wavesurfer.js accordingly.

Detecting Tab Switching with the Page Visibility API

The Page Visibility API exposes two key features:

  • document.hidden: A boolean indicating whether the page is currently hidden from the user.
  • visibilitychange: An event fired on the document whenever the visibility state changes.

Scenario 1: Auto-Pausing and Resuming Playback

A common user experience requirement is pausing audio when the user leaves the tab and resuming it only if it was playing prior to switching away.

Here is how to implement this pattern:

import WaveSurfer from 'wavesurfer.js';

// Initialize Wavesurfer instance
const wavesurfer = WaveSurfer.create({
  container: '#waveform',
  waveColor: '#4F4A85',
  progressColor: '#383351',
  url: '/audio-sample.mp3',
});

// Track whether the audio was actively playing before the tab was hidden
let wasPlaying = false;

function handleVisibilityChange() {
  if (document.hidden) {
    // Tab is hidden: check playback state and pause if running
    if (wavesurfer.isPlaying()) {
      wasPlaying = true;
      wavesurfer.pause();
    } else {
      wasPlaying = false;
    }
  } else {
    // Tab is visible again: resume only if it was playing previously
    if (wasPlaying) {
      wavesurfer.play();
      wasPlaying = false;
    }
  }
}

// Attach the visibility listener
document.addEventListener('visibilitychange', handleVisibilityChange);

Scenario 2: Maintaining Continuous Background Playback

If your application requires audio to keep playing while the user is in another tab (such as a podcast or music player), you should prevent unnecessary UI redraws while keeping the audio engine uninterrupted.

Browsers throttle requestAnimationFrame, causing waveform rendering updates to lag behind real-time playback. When the user returns to the tab, the visual playhead may jump abruptly.

To ensure smooth operation:

  1. Use the HTML5 Audio backend: Wavesurfer.js defaults to using Web Audio elements via the HTML Media Element under the hood in newer versions. Ensure your backend relies on standard HTML media elements, as browsers rarely throttle the underlying audio decode thread of media elements compared to complex Web Audio API graph nodes.
  2. Force a redraw on tab focus: Synchronize the waveform playhead immediately upon return so the visual state matches the current audio time:
document.addEventListener('visibilitychange', () => {
  if (!document.hidden && wavesurfer.isPlaying()) {
    // Force the waveform display to match current playback time
    const currentTime = wavesurfer.getCurrentTime();
    const duration = wavesurfer.getDuration();
    if (duration > 0) {
      wavesurfer.seekTo(currentTime / duration);
    }
  }
});

Cleaning Up Listeners

When tearing down the Wavesurfer instance (e.g., in single-page applications during component unmounting), remove the event listener to avoid memory leaks:

function destroyPlayer() {
  document.removeEventListener('visibilitychange', handleVisibilityChange);
  wavesurfer.destroy();
}
