How to Sync Two Wavesurfer.js Waveforms

Synchronizing two distinct audio waveforms in Wavesurfer.js is essential for comparative audio tools, multitrack players, and A/B testing interfaces. This article breaks down the primary technique for achieving sample-accurate synchronization between two separate Wavesurfer instances: bidirectional event bridging with state-lock guards. You will learn how to align playback, handle seeking, and prevent recursive feedback loops to keep both audio tracks and visual cursors perfectly aligned.

The Core Technique: Bidirectional Event Synchronization

The most effective way to keep two separate Wavesurfer instances synchronized is through bidirectional event listening paired with an execution guard (a boolean lock).

When Track A plays, pauses, or seeks, it triggers corresponding methods on Track B, and vice versa. However, directly mirroring these events causes an infinite feedback loop (Track A updates Track B, which in turn updates Track A). A synchronization flag prevents this recursion.

Implementing the State Lock

To prevent event loops, declare a boolean state variable such as isSynchronizing = false. When an interaction occurs on one waveform, set the flag to true, update the second waveform, and reset the flag to false.

1. Synchronizing Play and Pause

Ensure that starting or stopping playback on either instance instantly mirrors the state to the other:

  • Listen for the play event on Instance A, and call instanceB.play() only if isSynchronizing is false.
  • Listen for the pause event on Instance A, and call instanceB.pause() under the same condition.
  • Repeat the exact reverse bindings from Instance B to Instance A.

2. Synchronizing Seeks and Clicks

User interaction on a waveform—such as clicking or dragging the timeline—dispatches a seeking or interaction event.

When a user seeks on Waveform A:

  1. Check if isSynchronizing is active; if so, exit.
  2. Set isSynchronizing = true.
  3. Read the progress value (a normalized float between 0 and 1) or the precise current time via instanceA.getCurrentTime().
  4. Call instanceB.setTime(time) or instanceB.seekTo(progress).
  5. Reset isSynchronizing = false.

Mitigating Audio Drift

Even if playback starts simultaneously, independent HTML5 audio elements can experience slight timing drift over time due to differences in decoding, system performance, or sample rates.

To eliminate drift:

  • Designate a Master: Treat one instance as the "master" time source (typically the primary or longer track).
  • Periodic Correction: Listen to the master's timeupdate event. Compare master.getCurrentTime() with slave.getCurrentTime(). If the absolute difference exceeds a small threshold (such as 20–30 milliseconds), adjust the slave's playback position to match the master using slave.setTime().

Alternative: Shared Web Audio Context

If both tracks are loaded simultaneously and drift must be zero by design, use a single shared Web Audio AudioContext.

By configuring both Wavesurfer instances to route through the same AudioContext via Wavesurfer's backend options, both waveforms share a single hardware-level clock (AudioContext.currentTime). Combining a shared context with event-mirrored controls delivers the most accurate sync possible in the browser.
