Wavesurfer.js Unit Testing: Clean Teardown Strategies

Testing audio components powered by Wavesurfer.js presents unique challenges in unit testing environments like Jest or Vitest. Because Wavesurfer interacts directly with the HTML5 Canvas, DOM nodes, asynchronous media decoders, and the Web Audio API, improperly disposed instances can lead to memory leaks, lingering event listeners, and cross-test pollution. This guide outlines the essential unit testing strategies needed to ensure that every Wavesurfer.js instance is cleanly torn down and isolated between test runs.

Explicitly Invoke wavesurfer.destroy() in Teardown Hooks

The primary mechanism for cleaning up a Wavesurfer instance is its built-in destroy() method. This method removes canvas elements, detaches DOM event listeners, disconnects internal audio nodes, and unregisters internal event emitters.

Always invoke this method inside your test framework's standard post-test lifecycle hook (afterEach):

describe('AudioPlayer Component', () => {
  let wavesurfer;

  beforeEach(() => {
    wavesurfer = WaveSurfer.create({
      container: document.createElement('div'),
      url: '/test-audio.mp3',
    });
  });

  afterEach(() => {
    if (wavesurfer) {
      wavesurfer.destroy();
      wavesurfer = null;
    }
  });

  // Tests go here
});

Explicitly assigning the reference to null guarantees that the garbage collector can reclaim the instance memory.

Clear Host DOM Containers

When mounting Wavesurfer to elements attached to the global DOM (such as document.body), calling destroy() cleans up the internal canvas elements but may leave the parent container intact. To maintain a sterile environment:

  • Create dynamic container elements per test rather than relying on static HTML fixtures.
  • Remove the container from the DOM in the afterEach hook using container.remove() or reset the document body with document.body.innerHTML = ''.

Manage and Close Web Audio Contexts

Wavesurfer relies on an AudioContext to process sound. In standard unit testing environments like JSDOM, the Web Audio API is not natively implemented and must be mocked (e.g., using standardized-audio-context-mock or custom Jest stubs).

If you pass a custom AudioContext into Wavesurfer via the configuration options, wavesurfer.destroy() may not automatically close the context. To prevent dangling timers or background audio processing:

  1. Inject an explicit AudioContext during initialization.
  2. Close the context manually in your afterEach block:
afterEach(async () => {
  if (wavesurfer) {
    wavesurfer.destroy();
    wavesurfer = null;
  }
  if (audioContext && audioContext.state !== 'closed') {
    await audioContext.close();
    audioContext = null;
  }
});

Abort Pending Asynchronous Operations

Audio decoding, file fetching, and peaks processing are asynchronous. If a test completes while an audio buffer is still decoding, the completion callback may trigger in the middle of a subsequent test, leading to unpredictable failures.

  • Cancel In-Flight Requests: If fetching media over the network, ensure mock fetchers or AbortController instances associated with the load call are aborted.
  • Wait for Stable States: Avoid terminating a test in the middle of an asynchronous lifecycle hook. Wait for events like ready or catch and handle decoding errors explicitly before moving to test teardown.

Reset Web API and Animation Mocks

Wavesurfer uses requestAnimationFrame for timeline rendering and playhead tracking. When mocking requestAnimationFrame, cancelAnimationFrame, HTMLMediaElement prototypes, or Canvas 2D contexts:

  • Cancel any active animation frame requests inside the afterEach block.
  • Call jest.clearAllMocks() or vi.restoreAllMocks() to ensure call counts and spy implementations do not bleed across test boundaries.

Verify Clean Isolation with Leak Detection

To confirm that teardown strategies are working effectively across your suite, execute your test runner with leak-detection flags (such as jest --detectLeaks). If a test fails this check, inspect unclosed event subscriptions, global window listeners (such as resize observers created by responsive plugins), or uncollected canvas buffers.
