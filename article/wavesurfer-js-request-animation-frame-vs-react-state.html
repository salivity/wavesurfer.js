Wavesurfer.js: requestAnimationFrame vs React State

Tracking playback progress in audio-heavy applications requires high-frequency updates, but doing so via standard React state triggers excessive re-renders that hurt performance. Polling wavesurfer.getCurrentTime() inside a requestAnimationFrame loop provides a far superior approach by bypassing React's reconciliation cycle, aligning updates directly with the browser's display refresh rate, and keeping the user interface completely fluid.

The Overhead of React State Updates

When building an audio player with Wavesurfer.js, the most intuitive approach is often listening to the timeupdate or audioprocess event and pushing the current timestamp directly into a React state hook via useState.

However, playback events can fire anywhere from 4 to 60 times per second. Updating React state at this frequency causes the component—and potentially its child components—to re-render repeatedly. Each state update forces React through its virtual DOM diffing and reconciliation pipeline. When complex UI trees, waveform visualizers, or tracklists are involved, this overhead causes noticeable frame drops, input latency, and UI sluggishness.

Why requestAnimationFrame is Superior

Using requestAnimationFrame (rAF) to poll wavesurfer.getCurrentTime() decouples visual time updates from the React lifecycle entirely.

  1. Hardware-Synchronized Visuals: requestAnimationFrame executes callbacks just before the browser repaints, matching the user's monitor refresh rate (typically 60Hz, 120Hz, or 144Hz). This guarantees that time counters, custom playheads, and progress indicators animate as smoothly as possible without visual stutter or micro-jank.

  2. Zero Component Re-renders: Instead of passing the timestamp through React state to update a <span className="timer">, a rAF loop can mutate a direct DOM reference (ref.current.textContent = formattedTime). By writing directly to the DOM or an imperative canvas layer, the React render tree remains completely untouched during audio playback.

  3. Automatic Throttling and Power Efficiency: The browser automatically halts or throttles requestAnimationFrame callbacks when the user navigates away, switches tabs, or minimizes the window. Standard audio event listeners driving React state will continue to fire relentlessly in the background, consuming CPU cycles and draining mobile battery life to re-render invisible UI elements.

  4. Elimination of State Desynchronization: High-frequency state updates can lead to race conditions or batching delays, particularly during rapid scrubbing, seeking, or track changes. Polling getCurrentTime() directly from the underlying audio context in real-time ensures that your visual indicators always reflect the true, unbuffered playback position.

Implementation Pattern

To implement this pattern effectively:

  • Maintain your Wavesurfer.js instance inside a useRef.
  • Attach event listeners to Wavesurfer’s play, pause, and finish events.
  • On play, initiate a recursive requestAnimationFrame loop that reads wavesurfer.getCurrentTime() and updates target DOM elements directly via standard useRef handles.
  • On pause or finish, cancel the animation frame via cancelAnimationFrame to release resources.

By offloading the transient, millisecond-by-millisecond playback data to requestAnimationFrame and direct DOM mutation, React is left to do what it does best: manage application structure and macro-level state changes.
