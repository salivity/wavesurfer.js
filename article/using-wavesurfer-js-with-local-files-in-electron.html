Using Wavesurfer.js with Local Files in Electron

Integrating Wavesurfer.js into an Electron desktop application allows developers to render interactive audio waveforms directly from local storage. This article explains how to bridge Electron's security model with Wavesurfer.js by registering custom file protocols to stream local media, reading files into memory via the Node.js file system API, and handling native desktop drag-and-drop interactions.

The Security Challenge

In modern Electron applications, the renderer process operates in a sandboxed environment with contextIsolation enabled. Direct access to local filesystem paths (such as file://) is restricted by Chromium’s security policies, which often prevents Wavesurfer.js from fetching local audio files via standard URLs due to CORS and protocol restrictions. To resolve this, Electron provides several techniques to safely bridge local audio data to the renderer.

Method 1: Registering a Custom Protocol (Recommended)

The most performant way to load local audio into Wavesurfer.js is by registering a custom protocol in Electron's main process. This avoids loading entire audio files into memory at once and enables standard HTTP range requests for seeking and streaming.

In your main.js (or main process entry point), register a privileged protocol using protocol.handle:

const { app, BrowserWindow, protocol, net } = require('electron');
const path = require('path');
const { pathToFileURL } = require('url');

// Must be called before app is ready
protocol.registerSchemesAsPrivileged([
  { scheme: 'media', privileges: { secure: true, standard: true, supportFetchAPI: true, stream: true } }
]);

app.whenReady().then(() => {
  protocol.handle('media', (request) => {
    // Extract the local system path from the request URL
    const filePath = decodeURIComponent(request.url.slice('media://'.length));
    return net.fetch(pathToFileURL(filePath).toString());
  });

  // Create your BrowserWindow here...
});

In your renderer process, pass the custom protocol URL directly to Wavesurfer.js:

import WaveSurfer from 'wavesurfer.js';

const wavesurfer = WaveSurfer.create({
  container: '#waveform',
  waveColor: '#4F4A85',
  progressColor: '#383351',
});

// Load the local file using your registered protocol
const absolutePath = '/Users/username/Music/sample.mp3';
wavesurfer.load(`media://${encodeURIComponent(absolutePath)}`);

Method 2: IPC and Binary Data via Blobs

If you prefer using Electron's Inter-Process Communication (IPC) without creating a protocol, you can read the file as a buffer in the main or preload script and convert it to a Blob in the renderer.

  1. Preload Script (preload.js): Expose an API to read the audio file using Node's fs module:
const { contextBridge, ipcRenderer } = require('electron');
const fs = require('fs');

contextBridge.exposeInMainWorld('electronAPI', {
  readAudioFile: (filePath) => fs.promises.readFile(filePath)
});
  1. Renderer Process: Convert the returned buffer into a Blob and pass it to loadBlob:
async function loadAudioFromDisk(filePath) {
  const buffer = await window.electronAPI.readAudioFile(filePath);
  const blob = new Blob([buffer], { type: 'audio/mp3' });
  wavesurfer.loadBlob(blob);
}

Note: This method reads the entire file into memory before passing it to Wavesurfer.js, making it less suitable for very large audio files.

Method 3: Native Drag-and-Drop or HTML5 File Input

Electron renders native DOM elements with extended desktop capabilities. When a user drags an audio file onto the application window or selects it via <input type="file">, Chromium provides a standard Web API File object.

Because File inherits from Blob, it can be passed directly to Wavesurfer:

const dropZone = document.getElementById('drop-zone');

dropZone.addEventListener('dragover', (e) => e.preventDefault());

dropZone.addEventListener('drop', (e) => {
  e.preventDefault();
  const file = e.dataTransfer.files[0];
  
  if (file && file.type.startsWith('audio/')) {
    wavesurfer.loadBlob(file);
  }
});

Using custom protocols remains the standard architectural choice for desktop apps requiring programmatic access to local library paths, while loadBlob serves as the primary integration point for user-driven interactions.
