Wavesurfer.js Audio Decoding Quirks in Safari

Rendering interactive audio waveforms with Wavesurfer.js relies heavily on the browser’s Web Audio API, an area where Apple’s Safari (WebKit) engine behaves differently from Chromium and Gecko. Safari introduces unique challenges—including aggressive AudioContext suspension, strict memory ceilings on iOS, codec incompatibilities, and distinct behavior when executing decodeAudioData—that frequently lead to empty waveforms, playback failures, or silent errors. Understanding these quirks is essential for ensuring consistent, cross-browser audio visualization.

AudioContext Suspension and User Gestures

Safari enforces a strict autoplay policy that suspends the AudioContext until a direct user gesture (such as a click or touchend event) is registered.

When Wavesurfer.js initializes using the default WebAudio backend, it immediately attempts to create and use an AudioContext. In Safari, this context is instantiated in a suspended state. While decoding audio via decodeAudioData can technically occur while the context is suspended, attempting to query time domains, play audio, or connect certain audio nodes prematurely will fail silently.

To prevent initialization stalls, you must ensure the context is explicitly resumed on user interaction:

const wavesurfer = WaveSurfer.create({
  container: '#waveform',
  url: 'audio.mp3',
});

document.addEventListener('click', () => {
  if (wavesurfer.backend.ac.state === 'suspended') {
    wavesurfer.backend.ac.resume();
  }
}, { once: true });

ArrayBuffer Detachment in decodeAudioData

A prominent quirk in WebKit involves how AudioContext.decodeAudioData handles memory. When an ArrayBuffer is passed to decodeAudioData, WebKit "neuters" or detaches the buffer to transfer its memory directly to the audio decoding thread.

If an application attempts to reuse the original ArrayBuffer—for example, to decode the audio a second time or inspect its raw headers—Safari throws a TypeError: Cannot perform Construct on a neutered ArrayBuffer. When working with custom loaders or pre-fetched audio data in Wavesurfer.js, you must pass a clone of the buffer using .slice(0):

const bufferCopy = originalBuffer.slice(0);
wavesurfer.load(audioBlob, bufferCopy);

Codec and Container Incompatibilities

While Chrome and Firefox natively decode almost any WebM, Ogg, or Opus configuration, Safari’s support for these formats is inconsistent across versions:

  • WebM / Opus: Older versions of Safari and iOS Safari lack full support for Opus inside WebM containers. Passing a WebM file to decodeAudioData in Safari often rejects the promise with a generic EncodingError.
  • Variable Bitrate (VBR) MP3s: WebKit occasionally struggles to accurately calculate duration for certain VBR MP3 files during decoding. This discrepancy results in waveform peaks that drift out of sync with actual playback.
  • Non-Standard Sample Rates: Safari's underlying CoreAudio framework is sensitive to unusual sample rates (such as 11025 Hz or 96000 Hz). In some cases, decodeAudioData fails completely instead of resampling the stream automatically.

Standardizing audio assets on CBR (Constant Bitrate) MP3 or standard AAC/M4A files prevents the majority of WebKit decoding rejections.

iOS Memory Ceilings and WebProcess Terminations

On iOS Safari, each browser tab is subject to strict RAM limits imposed by the operating system. When Wavesurfer.js decodes a compressed audio file (like an MP3), decodeAudioData expands it into uncompressed 32-bit float PCM data in memory.

A 20 MB MP3 file can easily decompress into over 200 MB of raw PCM audio. If an application attempts to decode multiple tracks simultaneously or loads a single long audio file, iOS Safari will abruptly terminate the WebProcess, causing the webpage to reload automatically.

To bypass this limit on mobile devices, use pre-rendered waveform peaks instead of decoding the entire audio file in the browser:

const wavesurfer = WaveSurfer.create({
  container: '#waveform',
  url: 'audio.mp3',
  backend: 'MediaElement', // Relies on standard HTML5 audio streaming
  peaks: [[0.1, 0.5, 0.8, ...], [-0.1, -0.5, -0.8, ...]], // Pre-calculated server-side
});

Using the MediaElement backend combined with pre-computed peak data eliminates the need to invoke decodeAudioData entirely, bypassing Safari's memory limits and decoding inconsistencies.
