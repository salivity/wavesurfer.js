Domain Whitelisting for Embedded Wavesurfer.js

Securing embedded Wavesurfer.js audio players requires verifying that media files and playback interfaces run exclusively on approved domains. Because Wavesurfer.js is a client-side JavaScript library relying on the Web Audio API or HTML5 Media Elements, securing an embedded instance requires combining client-side host environment inspections, strict Cross-Origin Resource Sharing (CORS) configurations, and server-side HTTP header validations to effectively restrict playback to whitelisted sites.

Client-Side Hostname Inspection

When serving Wavesurfer.js via a standalone script, the player can inspect the execution context directly before initializing the audio visualizer.

  • Direct Hostname Matching: The script evaluates window.location.hostname against an array of approved domains. If the current hostname is absent from the whitelist, player initialization (such as WaveSurfer.create()) is aborted.
  • Iframe Ancestor Verification: If the player is delivered via an <iframe>, relying on window.location.hostname only reflects the player's host, not the embedding site. To verify the parent domain, the script checks document.referrer or queries window.location.ancestorOrigins (where supported). If the parent domain does not match the whitelist, the player interface remains inactive or displays an unauthorized notice.

Web Audio CORS Enforcement

Wavesurfer.js typically renders waveform visual data by fetching the audio file via an XMLHttpRequest or fetch request and decoding it into an AudioBuffer through the Web Audio API. This architectural requirement makes CORS an effective gatekeeper.

  • Strict Access-Control-Allow-Origin Headers: The media server or CDN hosting the audio tracks must not use a wildcard (*). Instead, it dynamically validates the incoming Origin header against an internal whitelist and returns the exact matching domain in the Access-Control-Allow-Origin header.
  • Denial of Web Audio Decoding: If an unauthorized website attempts to embed the player and point it to the media file, the browser's CORS policy blocks the binary audio transfer. Without the decoded audio data, Wavesurfer.js cannot render the waveform or process playback.

Server-Side Origin and Referer Filtering

Because client-side checks can be bypassed or manipulated by technically sophisticated users, the server delivering the audio assets and the embed scripts must perform validation checks on incoming HTTP requests.

  • HTTP Referer Verification: Media servers should inspect the Referer request header. If the referer’s base domain does not match the approved whitelist, the server returns an HTTP 403 Forbidden response.
  • HTTP Origin Header Matching: For cross-origin fetch operations initiated by Wavesurfer.js, the Origin header is automatically appended by the browser and cannot be altered by client-side JavaScript. Verifying the Origin on asset-serving endpoints ensures that the requesting context belongs to an authorized partner.

Time-Limited Signed Tokens

To counter referer spoofing and prevent direct link scraping, domain whitelisting is often paired with signed tokens. The parent domain requests a short-lived authorization token (such as a JSON Web Token) tied to both the user's session and the permitted host. When Wavesurfer.js requests the audio track or audio peaks data, it passes this token via URL query parameters or request headers. The server verifies that the token's embedded domain claim matches the current request environment before streaming the audio stream to the player.
